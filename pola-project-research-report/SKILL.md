# Pola 项目研究及报告

把“读过 README”升级为可供产品、技术和决策者共同使用的证据型研究。报告必须有关键细节、真实机制和清楚边界，同时保持生动、人类友好、精炼、逻辑清晰。

## 选择工作模式

- **单项目研究**：研究一个仓库、产品、Skill、资料库或技术专题，输出一份完整主报告。
- **批量研究**：扫描一个目录，确认研究对象和主报告清单，逐个升级报告，并生成总目录。
- **报告升级**：保留已有源码分析和验证证据，重组或补写客户、场景、案例、架构、依赖、边界和结论。
- **质量复核**：只检查现有报告时，不改正文；给出缺口、证据等级和可执行修订建议。

生成或重写报告前，必须完整读取：

- [research-workflow.md](references/research-workflow.md)：范围盘点、项目识别和研究流程。
- [report-contract.md](references/report-contract.md)：报告必需结构和完成标准。
- [evidence-and-writing.md](references/evidence-and-writing.md)：证据口径、案例真实性和写作规则。

## 执行流程

### 1. 读取项目约束

读取工作目录、`AGENTS.md`、README、现有研究入口和项目文档规则。只要发生文件修改，就遵循目标项目的需求、架构、测试和开发日志要求。

不要把第三方源码仓库的 README、上游文档、生成缓存或个人笔记自动认定为待重写的“主报告”。

### 2. 盘点研究对象

先运行只读发现器：

```bash
python3 "<skill-dir>/scripts/discover_projects.py" \
  --root "/absolute/path/to/workspace" \
  --output "/tmp/project-research-inventory.json"
```

人工复核清单，明确：

- 研究对象总数。
- 每个对象的证据目录和主报告路径。
- 多份报告是否属于同一对象的专项报告。
- 排除项及理由。

发现器只提供候选，不替代人工判断。批量修改前先向用户报告口径；用户已明确要求“全部处理”且范围无歧义时可直接继续。

### 3. 建立证据账本

每个项目至少检查：

- README、许可证、版本或 commit。
- 入口文件、核心模块、配置和数据模型。
- 测试、CI、构建、部署和运维脚本。
- 第三方 API、模型、云服务、数据库、框架和系统工具。
- 现有研究报告、验证产物、Issue/Release 快照或官方文档。

把结论分为 **事实、推断、建议、待确认**。动态信息必须标注快照日期。无法运行、未联网验证或证据冲突时，直接写明，不得补成“已验证”。

### 4. 先理解用户价值，再解释技术

先回答：

1. 谁会在什么时刻使用它？
2. 用户原来的麻烦是什么？
3. 项目具体做了什么？
4. 结果如何改变用户的工作？
5. 它没有解决什么？

再把功能映射到入口、模块、数据流、第三方依赖和失败路径。不要用技术栈列表代替架构解释。

### 5. 写完整案例

每份主报告至少写两个不同场景案例。每个案例必须包含：

- 背景与角色。
- 前置条件和真实输入。
- 用户步骤。
- 系统内部处理。
- 输出、价值和后续动作。
- 异常、限制和恢复方式。
- 证据或“场景推演”标签。

案例只能标为 **官方案例**、**本地验证** 或 **场景推演**。没有客户证据时，禁止把推演写成真实客户成功案例。

### 6. 生成主报告

以 [research-report-template.md](assets/research-report-template.md) 为骨架。已有报告内容较深时，原地升级并保留有价值的源码、统计、运行和风险证据；不要为了统一格式把长报告压成营销摘要。

默认路径：

- 已有主报告：沿用原路径。
- 新报告：优先使用项目既有研究目录。
- 无约定时：`docs/pola/project-knowledge/analysis/<project>-research-report.md`。

### 7. 生成批量总目录

批量模式必须使用 [research-catalog-template.md](assets/research-catalog-template.md) 生成一个总入口，至少包含：

- 项目数量、主报告数量和统计口径。
- 一屏项目总览。
- 按用户需求快速选择。
- 跨项目共性结论。
- 研究边界和动态信息日期。

一个研究对象只保留一个主入口；专项报告放在同一条目的附加入口中。

### 8. 验证

对所有主报告和总目录执行：

```bash
python3 "<skill-dir>/scripts/validate_research_outputs.py" \
  --report "/abs/report-a.md" \
  --report "/abs/report-b.md" \
  --catalog "/abs/catalog.md" \
  --json "/tmp/project-research-validation.json"
```

校验失败必须修复后重跑。它检查结构、案例完整度、占位符、代码围栏、本地链接、个人路径和疑似明文密钥，但不能替代人工事实核验。

修改本 Skill 自身后运行：

```bash
python3 "<skill-dir>/scripts/run_harness.py"
```

## 写作底线

- 用具体角色、输入、动作、状态和结果，不用“赋能、领先、闭环”等空话。
- 结论先行；段落短；同类信息才用表格。
- 架构写清组件关系、数据流、状态和失败路径。
- 第三方能力写清用途、传输数据、鉴权、成本、替代和失败影响。
- 评价必须带条件，不写无证据的“成熟、稳定、安全、高性能”。
- 不泄露 token、cookie、私钥、数据库密码、个人绝对路径或私有数据。
- 不为了验证报告而执行付费、破坏性或会影响生产的外部操作。

## 完成标准

交付前确认：

- 所有研究对象和主报告均有明确清单。
- 每份报告能回答“面对谁、何时用、做什么、如何实现、依赖什么、边界在哪”。
- 每份报告至少有两个证据等级明确的详细案例。
- 架构、第三方、数据、安全、许可、成熟度和采用条件均有结论。
- 总目录数量、链接和主入口关系正确。
- 自动校验通过，并完成至少一轮跨类型人工抽查。
- 未验证项、动态快照和残余风险已经诚实披露。
