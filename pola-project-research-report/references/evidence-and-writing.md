## 1. 证据等级

- **事实**：固定源码、配置、测试、运行记录、许可证或官方文档直接支持。
- **推断**：多个事实共同支持，但项目没有直接声明。
- **建议**：研究者对采用、试点、改造或替代的判断。
- **待确认**：证据不足、动态信息过期、环境无法运行或来源冲突。

案例另标：

- **官方案例**：官方明确展示，注明来源。
- **本地验证**：研究过程真实运行，注明输入和结果。
- **场景推演**：依据功能和代码构造，用来帮助理解，不代表真实客户。

## 2. 事实核验

### 可信度优先级

通常按以下顺序判断：

1. 固定版本的源码、配置和可重复测试。
2. 同版本官方文档、Release 和许可证。
3. 本地运行记录。
4. 维护者 Issue、Discussion 或演示。
5. README 营销性描述。
6. 第三方文章、榜单和搜索摘要。

优先级不是绝对的。例如本地运行环境与官方支持环境不同，应同时保留版本和环境说明。

### 动态事实

Stars、Issue、Release、价格、Provider、API、维护者、兼容性和法律政策都可能变化。写明日期和来源；采用前提示重新核验。

### 否定性结论

“没有找到”不等于“项目没有”。使用：

> 在本次固定快照和已检查的入口、配置、测试中未找到该能力；不排除外部服务或未纳入分支存在。

## 3. 生动但不编造

生动来自具体，而不是形容词。

优先写：

- 一个明确角色正在处理什么任务。
- 他拿到什么输入，先做什么，系统出现什么反馈。
- 哪个模块改变状态，外部依赖失败时看到什么。
- 最终产物如何进入下一步工作。

不要编造：

- 客户名称、收入、节省比例、性能数字或成功率。
- 未运行的命令结果。
- 不存在的功能、认证、SLA 或生产案例。

可以用场景推演，但必须显式标注并写出推演依据。

## 4. 精炼与逻辑

采用信息金字塔：

1. 先给结论。
2. 再给最关键的 3–5 个理由。
3. 最后给证据、例外和细节。

写作规则：

- 一段只解决一个问题，通常 2–5 句。
- 标题回答读者问题，不堆“概述、介绍、分析”。
- 使用具体名词和动词，删除“相关、一定程度、全面赋能”等弱表达。
- 表格只用于重复字段对照；复杂因果用短段落或流程图。
- 架构图后必须有文字解释，不能让图独自承担结论。
- 每个优势紧跟成立条件或代价。
- 最终结论不复述全文，只保留决策所需信息。

## 5. 常见坏味道

### README 改写

症状：功能、技术栈和安装步骤都来自 README，没有源码和测试证据。

修正：至少检查入口、核心模块、配置、测试和部署，再标出冲突。

### 技术名词墙

症状：“采用 React、FastAPI、Redis、Docker、AI”。

修正：解释各组件在执行链中的职责、状态和失败影响。

### 假案例

症状：“某知名企业使用后效率提升 80%”但没有来源。

修正：删除；改成有标签、有输入、有内部处理和边界的场景推演。

### 空泛评价

症状：“项目成熟、稳定、值得推荐”。

修正：写清测试、发布、维护、许可和运行证据，以及推荐成立的环境。

### 结构齐全但内容空

症状：每节只有一句话或占位符。

修正：校验只是下限；人工抽查关键结论是否能回到证据。

## 6. 改写示例

差：

> 该项目功能强大，可以帮助企业提升效率。

好：

> 面向需要每天筛选数百条公开更新的行业研究团队，项目把来源采集、去重、事件聚类和证据门禁串成一条流水线。研究员最终看到的是带原始出处、置信度和下一验证信号的事件，而不是一组重复新闻标题。它能缩短筛选路径，但不能替代投资或合规判断。

差：

> 使用了第三方大模型。

好：

> 摘要阶段调用外部模型 Provider，并传输清洗后的正文片段。API key 从环境变量读取；Provider 不可用时任务失败且没有本地降级模型。采用前需要核验数据保留政策、单次成本和超时重试策略。
